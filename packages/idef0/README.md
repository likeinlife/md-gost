# Диаграммы IDEF0

Библиотека строит контекстную диаграмму и каскадную декомпозицию из двух–шести
шагов. Автор задаёт функции, подписи стрелок и их получателей. Координаты,
точки ветвления и переносы текста рассчитываются при отрисовке.

## Диаграмма в Markdown

Для отчёта удобно описать диаграмму прямо в главе. Сборщик присвоит ей номер,
поставит подпись и разрешит ссылку `[@fig:release]`.

````markdown
```{.idef0 #fig:release caption="Разработка и проверка системы"}
block A1 : Разработать систему
block A2 : Проверить систему

input -> A1 : Задание
A1 -> A2 : Версия системы
A2 -> output : Проверенная система
control -> * : Политика качества
mechanism -> A1,A2 : Команда
A2 -> A1.control : Замечания на доработку
```
````

Первое объявление `block` открывает декомпозицию. Порядок блоков задаёт основную
цепочку. Каждая соседняя пара получает одну стрелку вида `A1 -> A2 : Подпись`.
Для дополнительной связи укажите роль у получателя — `.input` для входа слева
или `.control` для управления сверху. Обе роли доступны при прямой и обратной
связи, в том числе между соседями. Так можно вернуть результаты проверки на
вход разработки или передать указания сверху.

Для общего управления или механизма укажите `*`, для индивидуальной стрелки —
один код, для одной стрелки с ответвлениями — коды через запятую. У блока
может быть один внешний вход и один внешний выход. На каждую сторону управления
и механизмов допускаются одна общая стрелка и до четырёх групповых, а у каждого
блока — до шести индивидуальных.

Контекст начинается со строки `context`. Каждая следующая строка добавляет
отдельную подписанную стрелку на соответствующую сторону функции.

```text
context A0 : Разработать систему
input : Заявка
control : Договор
mechanism : Команда
output : Принятая система
output : Акт приёмки
```

Пустые строки и строки комментариев, начинающиеся с `#`, пропускаются.
Первое двоеточие отделяет команду от подписи. Внутри подписи можно использовать
двоеточия и задавать перенос через `\n`. Сборщик указывает строку ошибочной
команды относительно начала диаграммы.

Для рисунка в отдельном файле запишите тот же текст в `context.idef0`
и вставьте его в главу как `![Контекст предприятия](context.idef0){#fig:context}`.
В Python текстовую модель читает `idef0.parse_text(source)`.

## Цвет блоков, стрелок и подписей

По умолчанию контуры блоков, стрелки и текст чёрные, заливка блоков белая.
Укажите цвет у того элемента, который хотите выделить.

| Атрибут | Что окрашивает |
| --- | --- |
| `color` | Контур блока или стрелку целиком, включая наконечник, ветви и точки ветвления |
| `fill` | Заливку блока |
| `text_color` | Название и код блока или подпись стрелки |

Каждый атрибут принимает имя из палитры или HEX в формате `#RGB` либо
`#RRGGBB`. Регистр букв свободный. Имена палитры — `black`, `white`,
`gray`, `red`, `orange`, `yellow`, `green`, `teal`, `blue` и `purple`.
В Python их значения доступны в словаре `idef0.PALETTE`.

В `.idef0` атрибуты записываются перед двоеточием через пробел.
Например, у обратной стрелки ниже оранжевая линия и чёрная подпись.

```text
block A1 [color=blue fill=#eaf2fd text_color=#163c6b] : Подготовить проект
block A2 : Проверить проект
A1 -> A2 : Проект
A2 -> A1.control [color=orange] : Замечания
```

В Python те же имена доступны у блоков и стрелок. Для отдельной стрелки
в `Context`, списке `chain`, словарях входов и выходов или аргументе
`from_previous` передайте `Arrow` с подписью и цветами.

```python
from idef0 import Arrow, Decomposition

diagram = Decomposition()
diagram.step("A1", "Подготовить проект", color="blue", fill="#eaf2fd")
diagram.step("A2", "Проверить проект", from_previous=Arrow("Проект", color="blue"))
diagram.control("Замечания", source="A2", to="A1", color="orange")
diagram.output("Принятый проект", source="A2", text_color="green")
```

## Декомпозиция по шагам в Python

```python
from idef0 import Decomposition, draw

model = Decomposition()
model.step("A1", "Уточнить запрос")
model.step("A2", "Создать систему", from_previous="Требования")
model.step("A3", "Проверить систему", from_previous="Версия системы")

model.input("Заявка", to="A1")
model.output("Принятая система", source="A3")
model.control("Договор")
model.control("Бюджет", to="A2")
model.mechanism("Стенд", to=["A2", "A3"])
model.input("Предложения по изменениям", source="A3", to="A1")
model.control("Замечания на доработку", source="A3", to="A2")

fig = draw(model, style="report")
```

Параметр `from_previous` подписывает поток от предыдущего шага. У внешних
управлений и механизмов вызов без `to` добавляет общую стрелку. Параметр
`source` у `input` или `control` указывает, результат какого блока подаётся
на вход или управление выбранного получателя.

## Компактная запись в Python

Если перечень шагов и связей уже собран в данных, передайте его в `Waterfall`.
В `chain` должно быть на одну подпись меньше, чем блоков.

```python
from idef0 import Arrow, Block, Link, Waterfall

diagram = Waterfall(
    blocks=[
        Block("A1", "Уточнить запрос"),
        Block("A2", "Создать систему"),
        Block("A3", "Проверить систему"),
    ],
    chain=["Требования", "Версия системы"],
    inputs={"A1": "Заявка"},
    outputs={"A3": "Принятая система"},
    controls=[Arrow("Договор"), Arrow("Бюджет", to="A2")],
    mechanisms=[Arrow("Стенд", to=["A2", "A3"])],
    links=[
        Link("A3", "A1", "Предложения по изменениям", role="input"),
        Link("A3", "A2", "Замечания на доработку", role="control"),
    ],
)
```

Для одной общей стрелки подойдёт строка, например `controls="Договор"`.
При повторном коде блока, неизвестном получателе, петле или дублировании
одной и той же связи библиотека выдаёт `ModelError`.

Контекст в Python задаётся через `Context`. Каждая из четырёх сторон принимает
строку или последовательность подписей.

```python
from idef0 import Block, Context

diagram = Context(
    Block("A0", "Разработать систему"),
    inputs="Заявка",
    outputs=["Принятая система", "Акт приёмки"],
    controls="Договор",
    mechanisms="Команда",
)
```

## Отрисовка и переход на новый API

В `.plot` и внешнем `.py` сборщик предоставляет пакет `idef0`. Присвойте
модель переменной `diagram` для автоматической отрисовки. Чтобы выбрать
оформление, присвойте результат `fig = idef0.draw(model, style="report")`.
Сборщик принимает один результат — `diagram`, `fig` или `g`. Поле манифеста
`prefer_vector` выбирает SVG или PNG и для текстовой, и для Python-формы.
Для сборки установите основной пакет с зависимостями `.[plots]`. Отдельно
Python-библиотеку можно установить из `packages/idef0`.

Профиль `report` задаёт размеры для рисунка на печатном поле A4 и подбирает
шрифт с засечками. Для ручного изменения геометрии передайте объект `Layout`
вторым аргументом `draw`. При совместном использовании профиль выбирает
семейство шрифта, а `Layout` определяет геометрию и размеры текста.
Заголовки блоков переносятся с учётом ширины текста в выбранном шрифте.
Явный перенос `\n` сохраняется. Если внешняя подпись выходит за край рисунка,
библиотека увеличивает поля холста. Для печати проверьте читаемость рисунка
в масштабе страницы.

Для переноса прежних Python-диаграмм используйте следующие соответствия.

| Прежняя запись | Новая запись |
| --- | --- |
| Импорты из `idef0.models` | `from idef0 import Block, Context, Decomposition, Waterfall` |
| `flows` между соседними блоками | Подписи в `chain` или аргумент шага `from_previous` |
| `input_links`, `control_links` | `Link(..., role="input")` или `Link(..., role="control")` в `links` |
| `Port` во внешних входах и выходах | Словарь с кодом блока и подписью или методы `input`, `output` |
| Индивидуальные и групповые управления и механизмы | `Arrow(label, to=...)` или методы `control`, `mechanism` |
| `draw_context`, `draw_waterfall` | `draw(diagram)` |

## Галерея и проверки

Галерея в `e2e/img/` включает три контекстные диаграммы и каскады из двух–шести блоков. Файлы
`*-minimal.png` показывают один вход и один выход, `*-dense.png` — до четырёх
входов и выход каждого блока. `different.png`, `many.png`, `mixed.png` и
`long.png` показывают разные индивидуальные стрелки и длинные подписи.
В `nightmare.png` у каждого из шести блоков по пять индивидуальных управлений и механизмов,
а группы стрелок обслуживают по три блока.

Диаграмма выпуска ПО показывает четыре обратные связи на шести блоках.
Например, поддержка возвращает запросы на изменение на вход анализа требований
(A6 → A1), а испытатели передают замечания разработчикам по управлению (A4 → A3).
[Рисунок с обратными связями](e2e/img/feedback.png) · [Модель](e2e/feedback.py)

Два примера включены также в `example/example.docx`.

Из каталога `packages/idef0` выполните:

```bash
make gallery  # заново создать все PNG в e2e/img/
make test     # запустить тесты
make lint     # проверить Ruff и wemake-python-styleguide
make types    # проверить типы в строгом режиме
make check    # выполнить lint, types и test
```

Команды используют `uv`: при первом запуске он установит зависимости
библиотеки и группы `dev` в `.venv`. Сквозные тесты интеграции с документами
используют расположенный рядом каталог `packages/md-gost-build`.

Тесты проверяют границы модели и все 5456 поддерживаемых сочетаний внешних
входов и выходов для 2–6 блоков без создания изображения для каждого
сочетания. Галерея и небольшие сквозные тесты проверяют построение PNG и SVG,
автоматическую передачу IDEF0 и совместимость с Matplotlib. Тесты подписей
дополнительно проверяют горизонтальное направление входов, адресатов групп, отсутствие наложений
текста на блоки и друг на друга, в том числе в плотном примере. Проверки не
гарантируют читаемость всех возможных длин подписей — изображения следует
просматривать.

Ruff включает `select = ["ALL"]`; единственное явно отключённое правило —
`CPY001`, требующее уведомление о копирайте. Из несовместимых пар D203/D211
и D212/D213 Ruff автоматически выбирает по одному правилу.
