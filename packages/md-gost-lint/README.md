# md-gost-lint

Линтер исходников `.md`, из которых [`md-gost-build`](../md-gost-build/README.md)
собирает документы по ГОСТ. Проверяет то, что сборка проверить не может:
что раздел кончается выводом, а не таблицей, что в тексте нет жирного шрифта,
что ссылка вписана в предложение, а номера рисунков не набраны руками.

Команда `md-gost` живёт в [`md-gost`](../md-gost/README.md) и вызывает этот модуль.
Сборка по-прежнему запускает проверку глав отдельным процессом на стандартной библиотеке.

Таблицы с `|` и сложные Pandoc grid tables распознаются как единый блок.
Для grid tables `STYLE005` проверяет выравнивание и замкнутость границ,
прямоугольность объединений и полный разделитель шапки. Правила подписей,
ссылок, выделений и нумерации строк действуют для обоих форматов.
`--fix` сохраняет всю сетку, включая выравнивающие пробелы.
Синтаксис и пример приведены в [README сборщика](../md-gost-build/README.md#сложные-таблицы-объединения-и-многоуровневая-шапка).

## Запуск

```bash
md-gost lint                         # весь репозиторий
md-gost lint example/                # один документ
md-gost lint example/CHAPTER_1.md    # одна глава
md-gost lint --fix                   # исправить механическое
md-gost lint --list-rules            # перечень правил и их уровни
md-gost format example/              # выровнять таблицы и пробелы
md-gost format --check               # не записывать файлы
md-gost format --diff                # показать diff
```

Вывод — строки вида `путь:строка:колонка: уровень [ПРАВИЛО] пояснение`.

| Код | Когда |
|-----|-------|
| `0` | ошибок нет (предупреждения на код не влияют) |
| `1` | найдена хотя бы одна ошибка (`error`) |
| `2` | нечего проверять: путь не существует или это не `.md`/`.puml`/`.iuml` |

Опечатка в пути — это код `2` и сообщение в stderr, а не «замечаний нет»:
молчаливый ноль на несуществующем каталоге выглядел бы как пройденная
проверка. Существующий каталог без единого `.md` даёт код `0` и строку
«проверять нечего» в stderr.

Цель может быть каталогом, `.md`-главой, `.puml`/`.iuml`-диаграммой или ничем
(тогда берётся корень репозитория). Диаграмма, переданная напрямую, проверяется
как цепочка своих `!include` — Markdown-правила к ней не применяются. Каталог разворачивается в работы по манифестам `book.toml`:
проверяются только главы, перечисленные в `chapters`. Остальные `.md` в каталоге
документа линтер не трогает. Отдельный файл проверяется вместе с
контекстом своей работы, поэтому ссылка на `#bib:`-метку из `REFERENCES.md`
не считается битой.

Ключи:

| Ключ | Что делает |
|------|------------|
| `--fix` | применяет механические исправления (STRUCT008, STRUCT009, TYPO003, TYPO005) |
| `--strict` | считает предупреждения ошибками |
| `--rules A,B` | проверяет только указанные правила |
| `--ignore A,B` | пропускает указанные правила |
| `--format json` | машинный вывод |
| `--no-config` | игнорирует `mdlint.toml` |
| `--list-rules` | печатает правила с уровнями по умолчанию |

## Диагностика и автодополнение в редакторе

Установите пакет с поддержкой LSP из корня репозитория командой
`uv tool install '.[lsp]'`. Для Zed есть [расширение](../../editors/zed/README.md),
для VS Code и Cursor — [расширение](../../editors/vscode/README.md).
Другому LSP-клиенту укажите команду `md-gost lsp`, транспорт stdio и язык Markdown.

Сервер проверяет главы ближайшего `book.toml` в порядке `chapters`. Изменения
открытых глав видны сразу. Для закрытых глав он читает сохранённый текст.
Ошибки и предупреждения имеют те же коды и уровни, что и в CLI, включая
переопределения из `mdlint.toml`.

- В Zed нажмите `⌘.` на подчёркнутом месте, чтобы исправить лишний пробел,
  табуляцию или нумерацию заголовка. В VS Code и Cursor то же меню открывает
  `Ctrl+.` (`⌘.` на macOS). «md-lint: исправить всё в главе»
  применяет доступные исправления к текущему буферу с учётом `mdlint.toml`.
  LSP-клиент может запросить это действие по идентификатору `source.fixAll.md-gost`.
- Команда `editor: format` убирает лишние пробелы в тексте и выравнивает
  Markdown-таблицы, в том числе Pandoc grid tables с объединениями.
  Форматтер доступен и в Markdown-файлах вне `book.toml`.
  Команда `editor: format selections` форматирует выделенный текст. Для таблицы
  достаточно выделить одну ячейку. Повреждённую сетку форматтер пропускает.
- Введите `[@` для выбора метки. Например, после `[@tbl:` появятся таблицы
  текущей работы с подписями. После точки с запятой в групповой цитате
  предлагаются библиографические источники.
- После `[текст](#` выберите раздел по его идентификатору. В подсказке видны
  название раздела и файл главы. В ссылке вида `[текст](глава.md#`
  список ограничен заголовками указанного файла.
- На пустой строке вызовите дополнение вручную или наберите начало шаблона.
  `img` вставляет рисунок с подписью и меткой, `tbl` — обычную таблицу,
  `grid` — таблицу с сеткой, `link` — ссылку. В сниппете клавиша Tab
  переходит к следующему полю.
- После `![Подпись](` можно сразу набрать имя рисунка или расширение, например `.png`.
  Сервер заранее просматривает каталог с `book.toml` и два уровня подпапок.
  Если файл лежит в `diagrams/context.idef0`, ввод `context` предлагает весь путь. В списке рисунков
  доступны PNG, JPG, JPEG, SVG, PlantUML (`.puml`, `.iuml`), `.idef0` и графики `.py`.
  В более глубокую папку можно перейти, набрав её путь.
- В атрибуте листинга `file="…"` пути отсчитываются от `book.toml`.
  Для листинга `.python` начните вводить имя скрипта, для `.sql` — имя SQL-файла.
  В обычной ссылке `[текст](…)` путь отсчитывается от файла текущей главы.
- Введите `bib` на отдельной строке и выберите «Источник», чтобы вставить
  `<!-- #bib:source Описание источника -->`. Клавиша Tab переключает ключ
  и описание. Если такой ключ уже занят в работе, шаблон предложит свободный.
- Чтобы добавить источник прямо из текста, наберите `#bib:opachki` и вызовите
  быстрое исправление «Добавить источник bib:opachki». В тексте появится
  `[@bib:opachki]`, а в списке источников — запись с выделенным описанием.
  Действие доступно и на готовой ссылке `[@bib:opachki]`, если источник ещё
  не объявлен. К существующей записи можно перейти по F12.
  Сервер ищет `REFERENCES.md` среди глав из `book.toml`, затем главу с записями
  `#bib:` или заголовком списка литературы. Если список ещё не заведён,
  первая запись появится в конце текущей главы.
- Введите `код` для обычного блока, `листинг` для блока с подписью,
  `plantuml`, `plot` или `idef0` для диаграммы или графика. На открывающей
  строке после трёх обратных кавычек или тильд можно выбрать язык.
  В заголовке листинга Pandoc начните вводить `{.py`, чтобы выбрать Python.
  Сервер дополняет встроенный список языками из глав и из установленного
  Pandoc. Список Pandoc загружается один раз в фоне через `pypandoc`.
- Введите `формула`, `eq` или `$$`, чтобы вставить выключную формулу с меткой
  `#eq:` и строкой «где». В этой строке после `$` сервер предлагает обозначения
  из формулы над ней, в порядке появления в LaTeX.
- Начните новую строку обычной таблицы с `|` и выберите «Строка таблицы».
  Число ячеек берётся из шапки. Для таблиц с объединениями действует проверка
  геометрии `STYLE005`.
- На метке или ссылке доступны команды редактора для перехода к объявлению
  и поиска всех упоминаний.
- Наведите указатель на ключ ссылки, чтобы увидеть подпись таблицы, рисунка или
  листинга. Для библиографической ссылки подсказка показывает запись источника,
  для формулы — её выражение в LaTeX.

## Правила

### Структура раздела (`STRUCT`)

| Правило | Уровень | Что ловит |
|---------|---------|-----------|
| `STRUCT001` | error | раздел заканчивается вложением (таблица, рисунок, формула, листинг) вместо текстового вывода |
| `STRUCT002` | warning | раздел заканчивается списком |
| `STRUCT003` | error | в разделе нет ни одного абзаца — только вложения |
| `STRUCT004` | warning | два вложения подряд без текста между ними |
| `STRUCT005` | error | пропущен уровень заголовка, заголовок пуст или кончается точкой |
| `STRUCT006` | warning | одинаковые заголовки в одном файле |
| `STRUCT007` | error | последний раздел работы назван не «Заключение» |
| `STRUCT008` | error | точка после номера раздела в заголовке («## 3.1. Название») |
| `STRUCT009` | error | номер у структурного элемента («## 8 Заключение») |

Раздел — это отрезок от заголовка до следующего заголовка любого уровня либо
до конца файла. Заголовок, за которым сразу идёт подзаголовок, разделом не
считается и под `STRUCT001`/`STRUCT003` не попадает. Файл из одних
`#bib:`-маркеров (`REFERENCES.md`) структурные правила пропускают.

### Метки, ссылки, библиография (`REF`, `BIB`)

| Правило | Уровень | Что ловит |
|---------|---------|-----------|
| `REF001` | error | таблица без маркера `<!-- #tbl:label Подпись -->` |
| `REF002` | error | между маркером и таблицей вклинился другой блок |
| `REF003` | error | ссылка `[@…]` на необъявленную метку |
| `REF004` | error | метка объявлена дважды |
| `REF005` | warning | на таблицу или рисунок нет ни одной ссылки |
| `REF006` | warning | объект стоит раньше первой ссылки на него |
| `REF007` | error | номер рисунка, таблицы или листинга набран руками («таблица 3») |
| `REF008` | warning | источник объявлен, но не процитирован |
| `REF009` | warning | у диаграммы нет метки `#fig:` — сослаться на неё нечем |
| `REF010` | error | файл рисунка, диаграммы или листинга не найден |
| `REF011` | error | битый `!include` внутри `.puml` / `.iuml` |
| `EQ001` | error | маркер `<!-- #eq:… -->` оторван от формулы или несёт текст |
| `EQ002` | error | `$$…$$` набрано внутри абзаца — формула не получит номера |
| `EQ003` | error | номер формулы набран руками («в формуле (3)») |
| `EQ004` | error | расшифровка обозначения стоит отдельным абзацем от «где …» |
| `LST001` | error | у листинга есть и `file=`, и собственное тело |
| `LST002` | error | `lines=` задан без `file=` |
| `LST003` | warning | у листинга нет метки `#lst:` — сослаться на него нечем |
| `BIB001` | error | `[@bib:…]` стоит не в конце предложения |
| `BIB002` | error | больше одной ссылки `[@bib:…]` в абзаце |
| `BIB003` | warning | цитата в лабораторной работе |

`REF001`–`REF004` дублируют проверки сборки — но выдают все нарушения сразу,
с номерами строк, и до запуска pandoc.

`EQ001`–`EQ004` держат нумерацию формул в руках сборки — так же, как
`REF001`–`REF007` держат нумерацию таблиц и рисунков. Метка формуле
необязательна: номер она получает в любом случае, а `#eq:` нужна только затем,
чтобы на неё сослаться. Поэтому объявленная, но неиспользованная метка формулы
проходит по `REF005`, а формула без метки замечанием не считается.

Листингом считается блок кода с подписью `caption="…"`, меткой `#lst:` или
атрибутом `file="…"` — только такой блок нумеруется и попадает под правила
вложений. Блок кода без всего этого остаётся частью текста: ни `STRUCT001`, ни
`LST003` к нему не применяются.

`REF010` проверяет путь из `![…](diagrams/scheme.puml){#fig:label}` так же, как
это делает сборка: относительно каталога работы (того, где лежит `book.toml`).
`REF011` идёт дальше — читает найденный `.puml` и проверяет его `!include`
рекурсивно, резолвя каждый путь относительно файла с директивой, как это делает
сам PlantUML. Внешние `!includeurl`, элементы стандартной библиотеки
(`!include <archimate/Archimate>`) и пути из переменных пропускаются: на диске
их нет и быть не должно.

### Оформление текста (`STYLE`) и типографика (`TYPO`)

| Правило | Уровень | Что ловит |
|---------|---------|-----------|
| `STYLE001` | error | `**жирный**` вне заголовка и строки заголовка таблицы |
| `STYLE002` | warning | ссылка скобочной пометкой «(таблица [@tbl:x])» |
| `STYLE003` | warning | подпись пустая, со строчной буквы или с точкой в конце |
| `STYLE004` | warning | список из одного пункта |
| `STYLE005` | error | в строках таблицы разное число ячеек |
| `STYLE006` | error | номер строки внутри ячейки («1. Первая стадия») |
| `TYPO001` | warning | дефис вместо тире между словами |
| `TYPO002` | warning | прямые кавычки `"` вместо «ёлочек» |
| `TYPO003` | warning | два пробела подряд, пробел перед знаком препинания |
| `TYPO004` | error | латиница внутри русского слова (подменённые буквы) |
| `TYPO005` | warning | пробелы в конце строки, табуляция |
| `TYPO006` | error | строка начинается с тире: список, набранный не дефисом |

`--fix` исправляет `STRUCT008`, `STRUCT009`, `TYPO003` и `TYPO005` — то, где
однозначно понятно, как должно быть. Остальное требует решения автора и
правится руками. Содержимое ``` ```plantuml ```-блоков, блоков кода,
листингов и `$$…$$`-формул не проверяется и не правится: это разметка, а не
проза.

### Манифест (`BUILD`)

| Правило | Уровень | Что ловит |
|---------|---------|-----------|
| `BUILD001` | warning | `.md` лежит в каталоге работы, но не указан в `book.toml` |
| `BUILD002` | error | глава указана в `book.toml`, но файла нет |
| `BUILD003` | error | глава начинается не с заголовка |

## Конфигурация

Уровни правил задаются в `mdlint.toml`. Конфигов может быть несколько: они
**каскадом** применяются от корня репозитория к каталогу проверяемого файла,
и ближайший побеждает. Общий тон задаёт корневой, а отдельная работа держит
свои послабления у себя, рядом с `book.toml`:

```
mdlint.toml                 базовые уровни для всего репозитория
docs/report/mdlint.toml     послабления только этого документа
```

```toml
skip = ["drafts/*"]       # файлы, которые не проверяются вовсе

[rules]
STRUCT002 = "off"         # уровень правила для всего, что ниже этого файла

[paths."CHAPTER_*.md"]    # fnmatch по пути относительно самого mdlint.toml
STRUCT004 = "off"
```

Уровни: `error`, `warning`, `off`. Шаблоны в `[paths.…]` и `skip` считаются от
каталога, где лежит конфиг, — документу не нужно знать свой путь от корня
репозитория. Внутри одного файла совпадения применяются сверху вниз, поэтому
узкие шаблоны пишутся последними. `--no-config` отключает всю цепочку.

Послабление ставится там, где оно верно: правило, неуместное для одной работы,
выключается в её собственном `mdlint.toml`, а не в корневом.

## Связь со сборкой

`md-gost build` запускает проверку глав перед pandoc: ошибки прерывают сборку,
предупреждения печатаются. Обойти проверку можно флагом:

```bash
md-gost build --no-lint example/
```

Если нет `packages/md-gost-lint/md_lint.py` и модуль `gost_lint` не установлен,
сборка пропускает проверку Markdown.

После постобработки `.docx` сборка запускает отдельный
[`docx-post-lint`](../md-gost-postlint/README.md). Он читает `word/document.xml` из
OOXML-пакета и проверяет свойства таблиц и размеры встроенных изображений.
Эта проверка не заменяет визуальную проверку PDF: координаты фактических
страниц в `.docx` не хранятся, их рассчитывает редактор при верстке.

## Устройство

Команды `md-gost lint` и `md-gost lsp` используют одну модель документа и один набор правил.

| Модуль | Назначение |
|--------|------------|
| `gost_lint/markdown/` | Парсер Markdown, блоки, метки, ссылки и их координаты в исходном тексте |
| `gost_lint/work.py` | Чтение манифеста и глав, необходимых для проверок между файлами |
| `gost_lint/rules/` | Реестр правил и проверки документов и работ |
| `gost_lint/runner.py` | Применение правил к выбранным главам с учётом уровней из конфигурации |
| `gost_lint/app.py` | Команда `md-gost`: lint, format, build, postlint, lsp |
| `gost_lint/cli.py` | Проверка глав и вывод отчёта |
| `gost_lint/lsp/` | Диагностика открытых файлов, переходы по ссылкам и автодополнение |

Из исходного дерева линтер запускается командой `python3 md_lint.py` из каталога инструмента. Для языкового сервера нужна дополнительная зависимость `pygls`, которая устанавливается с опцией `.[lsp]` из корня репозитория.

Правило — это функция-генератор с декоратором `@rule(id, level, summary)`.
Область видимости `file` (один документ) или `work` (все главы работы сразу —
для ссылок, меток и библиографии). Регулярные выражения применяются к блокам,
а не к сырым строкам, поэтому правило не может сработать внутри диаграммы.

## Проверки кода

```bash
cd packages/md-gost-lint
uvx ruff check .      # стиль и типичные ошибки (то же гоняет pre-commit)
uvx ruff format .     # раскладка кода (тоже в pre-commit)
uvx pyrefly check     # типы, режим strict
```

Настройки обоих — в `pyproject.toml` этого инструмента: он самостоятельный
продукт, общей конфигурации на репозиторий нет.

## Тесты

```bash
cd packages/md-gost-lint
uvx pytest                      # весь набор, около секунды
uvx pytest tests/test_rules.py  # только правила
```

Вместо `uvx` годится любой рабочий `pytest` в окружении; своих зависимостей у
линтера нет, venv ему не нужен.

| Файл | Что проверяет |
|------|---------------|
| `tests/test_rules.py` | каждая фикстура даёт ровно известный набор правил |
| `tests/test_cli.py` | коды возврата, `--strict`, `--rules`, `--fix`, JSON |
| `tests/test_config.py` | каскад `mdlint.toml`, шаблоны путей, `skip` |
| `tests/test_document.py` | блочный парсер: границы блоков, метки, номера строк |

Набор правил в `test_rules.py` закреплён точно, а не «не меньше чем»: новое
правило, начавшее срабатывать на старом тексте, роняет тесты — и это нужное
поведение, потому что иначе правило тихо размножит замечания по всем работам.
Отдельный тест прогоняет линтер по всему репозиторию: замечания там ожидаемы,
исключение — нет.
