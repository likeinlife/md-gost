# md-gost-build

Сборка `.docx` по ГОСТ из директории с Markdown-главами. Один вызов:

```bash
md-gost build path/to/dir/
```

Установите команды из корня репозитория через `uv tool install .` или в
виртуальное окружение через `uv pip install .`. Порядок установки и обновления
описан в [README репозитория](../../README.md#установка-команд). Для графиков
используйте `uv tool install '.[plots]'` или `uv pip install '.[plots]'`.


Директория должна содержать манифест `book.toml` (порядок глав и имя
выходного файла). Инструмент сам отрендерит PlantUML-диаграммы, проставит
сквозную нумерацию рисунков/таблиц, соберёт список литературы и применит
ГОСТ-стили оформления.

## Требования

Нужны Python 3.11 или новее, Pandoc 3.9.x и, если в главах есть диаграммы,
Java, PlantUML и Graphviz (`dot`). Команды Python ставятся из корня репозитория,
см. [README репозитория](../../README.md#установка-команд). После `winget`,
`choco`, Homebrew и `setx` откройте новый терминал.

Проверка:

```bash
pandoc -v
java -version
dot -V
```

Python-зависимости (`pypandoc`, `python-docx`, `lxml`) устанавливаются вместе
с пакетом.

### Pandoc

Страница установки: <https://pandoc.org/installing.html>.

macOS:

```bash
brew install pandoc
```

Windows:

```powershell
winget install --source winget --exact --id JohnMacFarlane.Pandoc
```

Либо скачать бинарник через pypandoc. Каталог по умолчанию —
`%LOCALAPPDATA%\Pandoc` на Windows и `~/Applications/pandoc` на macOS.
Сборка спрашивает путь у `pypandoc.get_pandoc_path()` и находит этот файл,
даже если каталог не в `PATH`. Из корня репозитория:

```bash
uv run --with pypandoc python -c "import pypandoc; pypandoc.download_pandoc()"
```

Если pypandoc уже импортируется: `python -c "import pypandoc; pypandoc.download_pandoc()"`.
Ветка 3.9: `download_pandoc(version='3.9')`.

### Graphviz

`dot` нужен PlantUML для диаграмм, которые он не раскладывает сам.
Диаграммы последовательности обычно рисуются и без него. Нет `dot` в `PATH` —
сборка пишет предупреждение и продолжает работу.

macOS:

```bash
brew install graphviz
```

Windows, страница загрузки <https://graphviz.org/download/>:

```powershell
winget install graphviz
winget install --source winget --exact --id Graphviz.Graphviz
choco install graphviz
```

Если `dot -V` в новом терминале не находится, добавьте в `PATH` каталог `bin`
Graphviz.

### PlantUML

Проект: <https://github.com/plantuml/plantuml>.
Релиз: <https://github.com/plantuml/plantuml/releases/tag/v1.2026.10>.

macOS (формула ставит команду `plantuml` и Java):

```bash
brew install plantuml
plantuml -version
```

Jar для Windows и для любой системы, где команды `plantuml` нет. Скачайте
`plantuml.jar` из релиза (тот же файл, что `plantuml-1.2026.10.jar`) и
положите его в каталог, например `K:\user\Apps\Plantuml\plantuml.jar`.
Для этого jar нужна Java 17 или новее. Файл `plantuml-java8-1.2026.10.jar`
в том же релизе — сборка для Java 8; укажите его через `PLANTUML_JAR`.

Java на Windows:

```powershell
winget install --source winget --exact --id EclipseAdoptium.Temurin.21.JDK
```

Java на macOS, если формула `plantuml` не используется:

```bash
brew install --cask temurin
```

Поиск, первое совпадение:

1. `PLANTUML_JAR` — полный путь к jar, имя файла любое.
2. `PLANTUML` — полный путь к программе или к jar.
3. Команда `plantuml` в `PATH` (`plantuml.exe` на Windows, скрипт Homebrew на macOS).
4. Файл `plantuml.jar` в любом каталоге из `PATH`.
5. `plantuml.bat` или `plantuml.cmd` в `PATH`, и `plantuml.jar` в том же каталоге.

`shutil.which("plantuml")` на Windows смотрит только `PATHEXT` (`.exe`, `.bat`,
`.cmd`, …). Jar этим поиском не находится: сборка отдельно просматривает
каталоги `PATH`. Pandoc не запускает `.bat` и `.cmd`. Обёртка годится, когда
`plantuml.jar` лежит рядом: тогда вызывается `java -jar`. Имя
`plantuml-1.2026.10.jar` по `PATH` не ищется — переименуйте файл в
`plantuml.jar` или задайте `PLANTUML_JAR`.

Windows, переменная для новых терминалов:

```powershell
setx PLANTUML_JAR "K:\user\Apps\Plantuml\plantuml.jar"
```

Тот же каталог можно добавить в пользовательский `PATH`, оставив имя
`plantuml.jar`. Проверка:

```powershell
java -jar K:\user\Apps\Plantuml\plantuml.jar -version
```

macOS:

```bash
export PLANTUML_JAR="$HOME/Apps/plantuml.jar"
```

Без Java подойдёт нативный файл из того же релиза:
`native-plantuml-windows-amd64-1.2026.10.zip` или
`native-plantuml-macos-arm64-1.2026.10.zip`. Распакуйте его и укажите
`PLANTUML` на исполняемый файл, либо положите файл в `PATH` под именем
`plantuml.exe` (Windows) или `plantuml` (macOS).

## Быстрый старт

Из корня репозитория установите пакет с зависимостями для графиков и соберите пример:

```bash
uv tool install '.[plots]'
md-gost build example/
```

Готовый пример в корневом каталоге `example/` показывает все приёмы оформления сразу, включая
графики Seaborn и две диаграммы IDEF0. Их исходники можно использовать как шаблон
для своего документа. Дополнение `.[plots]` требуется для Python-графиков и IDEF0.

## Манифест `book.toml`

Кладётся в корень директории с главами. Формат — TOML:

```toml
output = "thesis.docx"          # имя выходного файла (рядом с book.toml)

chapters = [                     # главы строго в порядке сборки
  "INTRO.md",
  "CHAPTER_1.md",
  "CHAPTER_2.md",
  "REFERENCES.md",
]
```

- `chapters` — **обязательное** поле. Порядок в списке = порядок в документе.
  Только перечисленные файлы попадают в сборку; остальные `.md` игнорируются.
- `output` — необязательное, по умолчанию `output.docx`.
- `toc` — необязательное, по умолчанию `true`. `toc = false` собирает документ без
  оглавления «Содержание».
- `number_sections` — необязательное, по умолчанию `false`. Включает
  автоматическую нумерацию разделов (см.
  [«Нумерация разделов»](#нумерация-разделов)).
- `page_break_before_h1` — необязательное, по умолчанию `true`. Каждый
  заголовок первого уровня начинается с новой страницы. `false` собирает
  документ сплошным текстом: для отчёта разрыв перед главой нужен, для
  короткой лабораторной, где разделы лежат на первом уровне, он раздувает
  работу в несколько раз. Один конкретный заголовок переносится классом
  `.page`, см. [«Заголовки и главы»](#заголовки-и-главы).
- `prefer_vector = true` — генерировать диаграммы PlantUML, IDEF0 и графики Python в
  SVG. По умолчанию `false`: используется PNG. Готовые PNG, JPEG и SVG
  вставляются в исходном формате независимо от настройки. Для SVG, созданных
  при сборке, растровая копия не гарантируется: отображение зависит от версии Word.
- Все пути относительны директории с манифестом.

Чтобы включить рамку ГОСТ с основной надписью, добавьте таблицу `[frame]`
(см. раздел [«Рамка ГОСТ»](#рамка-гост-основная-надпись)):

```toml
[frame]                         # само наличие таблицы включает рамку
author = "Иванов И.И."          # Разраб.
checker = "Петров П.П."         # Провер.
title = "Отчёт по практике"     # наименование документа
org = "ДГТУ, кафедра «ИТ»"       # организация
designation = "ДП.090301.001"   # обозначение документа
sheets = "12"                   # Листов (всего)
first_sheet = "1"               # номер листа на первой странице
page_start = 1                  # с какого номера начинать нумерацию
```

Любой ключ можно опустить — подставится значение по умолчанию. Если рамка нужна
со стандартными значениями, достаточно написать `frame = true` (без таблицы).

### JSON Schema для редактора

Схема [`book.schema.json`](book.schema.json) описывает поля манифеста и помогает
редактору подсказывать параметры и замечать опечатки. Для редактора с поддержкой
TOML Schema можно указать путь к ней в начале `book.toml`, например для
корневого каталога `example/`:

```toml
#:schema ../packages/md-gost-build/book.schema.json
```

Путь в комментарии отсчитывается от манифеста. Схема проверяет структуру и типы;
наличие файлов глав и допустимость пути `output` проверяет сама сборка. Неизвестные
ключи схема отмечает как ошибки, хотя сборщик их игнорирует.

После изменения полей `Manifest` или значений в `gost_builder/frame/settings.py` обновите
схему командой `python packages/md-gost-build/generate_book_schema.py` из корня
репозитория. Тест проверяет, что сохранённая схема соответствует генератору.

## Синтаксис разметки

### Заголовки и главы

- `#` — заголовок 1-го уровня (стиль `Heading 1`, с новой страницы, если
  включён `page_break_before_h1`).
- `##` — заголовок 2-го уровня (`Heading 2`).
- `###` — заголовок 3-го уровня (`Heading 3`).
- В оглавление (TOC) попадают уровни 1–2.
- Класс `.page` начинает с новой страницы только этот заголовок, на любом
  уровне: `# Заключение {- .page}`, `## Подраздел {.page}`. Класс пишется
  в тех же фигурных скобках, что и `{-}`. При включённом
  `page_break_before_h1` заголовок первого уровня по-прежнему открывает
  одну новую страницу. Заголовок, который сборка понижает до жирного
  абзаца («Диаграмма», «модель данных»), класс не переносит.

Особые случаи (обрабатывает lua-фильтр автоматически):

- `# Глава N. Название` → в тексте и TOC станет `N. Название`.
- `## Выводы по главе` → понижается до **жирного абзаца** и убирается из TOC.
- Подзаголовок, содержащий слово `Диаграмма` или `модель данных`, понижается
  до жирного абзаца, а его текст используется как подпись следующего рисунка.

### Нумерация разделов

По умолчанию номер раздела — часть текста заголовка, его набирает автор
(`## 1.2 Требования`). Работа может отдать нумерацию сборке:

```toml
number_sections = true
```

Тогда номера из исходника **убираются совсем**, а сборка проставляет их сама:

```markdown
# Введение {-}                        →  Введение
# Анализ предметной области           →  1 Анализ предметной области
## Характеристика предметной области  →  1.1 Характеристика предметной области
### Требования к системе              →  1.1.1 Требования к системе
# Заключение {-}                      →  Заключение
```

- Нумерация сквозная по всему документу, а не по файлу: счётчик второго уровня
  сбрасывается на каждом заголовке первого уровня, третьего — на каждом втором.
- Отсчёт идёт от самого верхнего **нумеруемого** заголовка, а не от уровня 1.
  Если первый уровень занят названием работы под `{-}`, разделы второго уровня
  получат 1, 2, 3, а не 0.1, 0.2 (так делает `--number-sections` у pandoc,
  поэтому нумерует сборка сама).
- `{-}` — обычный атрибут pandoc (полная форма `{.unnumbered}`). Им помечаются
  разделы, которые по ГОСТ номера не имеют: «Введение», «Заключение» и прочие.
  «Перечень использованных информационных ресурсов» сборка создаёт сама и сама
  же помечает — делать с ним ничего не нужно.
- Номер отделяется от названия пробелом и печатается тем же шрифтом, что и
  заголовок; в «Содержание» он попадает вместе с названием.
- Заголовок, в котором номер уже набран руками, прерывает сборку: pandoc
  добавил бы к нему свой и получилось бы «1.2 1.2 Требования». Это же
  относится к форме `# Глава 3. Название`.

Флаг независим от остальных и включается в манифесте конкретного документа.
Если разделы лежат на первом уровне, обычно нужен и
`page_break_before_h1 = false` — иначе каждый раздел начнётся с новой
страницы.

### Приложения

Добавьте файлы приложений в конец `chapters` в `book.toml` в порядке их вывода.
Приложение также можно оформить в конце уже подключённого Markdown-файла.
Начните его заголовком первого уровня и укажите одну кириллическую букву.
Идентификатор в фигурных скобках нужен для ссылки из текста.

```markdown
# Приложение А. Листинг программы {#appendix-listing}
```

Ссылка из основной части оформляется как
`Исходный код приведён в [приложении А](#appendix-listing).`
В собранном документе текст ссылки чёрный — и до перехода, и после него.

Каждое приложение начинается с новой страницы, в том числе при
`page_break_before_h1 = false`. Обозначение «Приложение А» и название под ним
выравниваются по центру. Регистр букв берётся из исходного заголовка.
Заголовок включается в содержание при `toc = true`. Перечень использованных
информационных ресурсов размещается перед первым приложением.

При `number_sections = true` сборка нумерует разделы основной части.
Обозначение приложения и номера его подразделов задаются в Markdown.
Нумерация страниц и подписей остаётся сквозной. Приложение может состоять из
одного листинга, рисунка или таблицы.

По умолчанию используется книжный А4. Класс `.landscape` задаёт альбомную
ориентацию, а атрибут `paper=a3` выбирает А3. Обе настройки можно указать
в одном заголовке.

```markdown
# Приложение Б. Матрица проверок {#appendix-validation .landscape paper=a3}
```

Формат и ориентация действуют на всех страницах приложения. Сборка вставляет
разрыв раздела Word на границе основной части и приложений, а также при смене
формата или ориентации. Рамка и основная надпись применяются к основной части.
На страницах приложений сквозной номер выводится внизу по центру.

Название приложения выводится один раз. Длинные таблицы переходят на следующую
страницу автоматически, а шапка таблицы повторяется. В каталоге `example/`
показано многостраничное альбомное приложение между двумя книжными.

### Основной текст и списки

Обычный абзац оформляется стилем `Normal` (Times New Roman 14 pt, выравнивание
по ширине, интервал 1,5, абзацный отступ 1,25 см). Ничего особого делать не
нужно — просто пишите текст.

Списки — обычный Markdown:

```markdown
- маркированный пункт          1. нумерованный пункт
- ещё пункт                    2. ещё пункт
```

Маркер `-` в выходном документе заменяется на тире `–`, шрифт пунктов
выравнивается под ГОСТ (TNR 14, интервал 1,5, маркер на отступе 1,25 см).

### Рисунки: PlantUML

Блок с классом `plantuml` рендерится в PNG или SVG и получает подпись
`Рисунок N – ...` (стиль `GOSTImageCaption`, по центру):

````markdown
```{.plantuml #fig:usecase caption="Диаграмма вариантов использования"}
actor User
User --> (Войти)
```
````

- `#fig:usecase` — *необязательная* метка для перекрёстной ссылки.
- `caption="..."` — *необязательный* текст подписи. Если не задан, берётся
  заголовок ближайшего раздела (или текст «Диаграмма»).
- `@startuml/@enduml` можно не писать — добавятся автоматически.
- Нумерация рисунков сквозная по всему документу.

### Рисунки: файлы `.puml` и `.iuml`

Диаграмму не обязательно писать прямо в главе: её можно держать отдельным
файлом и вставлять как изображение.

```markdown
![Схема развёртывания системы](diagrams/deployment.puml){#fig:deploy}
```

Путь — относительно директории с главами (той, где `book.toml`). Поддерживаются
расширения `.puml` и `.iuml`; разницы между ними нет, сборка смотрит на
содержимое файла, а не на его имя.

Такой файл рендерится в выбранный формат и попадает в документ так же, как inline-блок: та
же сквозная нумерация «Рисунок N – ...», те же метки `#fig:` и ссылки
`[@fig:...]`, та же подгонка под полосу набора. Подпись берётся из `[...]`,
из атрибута `caption="..."` или из заголовка ближайшего раздела — в этом
порядке.

Что стоит знать:

- **Относительные `!include` внутри файла работают.** Файл не копируется в
  кеш: сборка пишет рядом с остальными диаграммами обёртку вида
  `@startuml` / `!include <абсолютный путь к файлу>` / `@enduml`, а PlantUML
  разрешает включения относительно того файла, где они написаны. Поэтому
  `!include style.iuml`, лежащий рядом с диаграммой, находится.
- **`@startuml/@enduml` в файле необязательны.** Файл-фрагмент (обычно это и
  есть `.iuml`) вставляется как есть; файл с полной диаграммой — своим блоком.
  Если блоков в файле несколько, вставляется первый.
- **Тип диаграммы сохраняется:** обёртка повторяет директиву файла, так что
  `@startmindmap`, `@startjson` и прочие не-UML диаграммы рендерятся тоже.
- Отсутствующий файл прерывает сборку (`diagram file not found: ...`).
- Файлы диаграмм в `book.toml` не перечисляются: в `chapters` только `.md`.
  Коммитятся они вместе с главами.

### Рисунки: Python, Matplotlib и Seaborn

Для графиков с данными можно использовать Python-блок `.plot`. Возможность
необязательная: PlantUML и остальные работы собираются без этих библиотек.
Когда в главе есть `.plot`, установите Matplotlib и Seaborn в окружение сборки:

```bash
uv tool install --force '.[plots]'  # из корня репозитория
```

Блок выполняется как Python-код при сборке. В нём доступны имена `plt`
(Matplotlib pyplot) и `sns` (Seaborn); можно сохранить фигуру как `fig` (или
Seaborn `FacetGrid` как `g`) либо работать с текущей фигурой pyplot. Например:

````markdown
```{.plot #fig:skills caption="Распределение оценок по критериям"}
fig, ax = plt.subplots(figsize=(7, 3.5))
sns.barplot(x=[4.2, 3.6, 4.7], y=["Полнота", "Актуальность", "Доступность"],
            ax=ax, color="#4472C4")
ax.set(xlim=(0, 5), xlabel="Средняя оценка", ylabel="")
```
````

Входные данные можно задать списками или загрузить из файла. Дополнительные
библиотеки вроде `pandas` устанавливаются отдельно, если они нужны. График
автоматически сохраняется в выбранный формат (PNG — 300 dpi) и оформляется как обычный рисунок:
получает сквозной номер, подпись и метку для `[@fig:skills]`.
Атрибуты `#fig:...` и `caption="..."` необязательны; без подписи используется
заголовок ближайшего раздела. Широкие и высокие изображения затем подгоняются
под полосу набора общей обработкой рисунков.

Блок запускается локально на машине сборки, поэтому выполняется как обычный
Python-код и может читать доступные ей файлы. Изображение создаётся в
`.md-to-gost/img/` и не добавляется как отдельный исходник. Для растрового
экспорта используется headless backend Matplotlib; функции Seaborn, которые
принимают `ax=`, удобно комбинировать с ручной настройкой осей и фигуры.

Объёмный график можно вынести в отдельный файл `.py` в каталоге работы и
вставить как изображение. Подпись задаётся alt-текстом, метка — атрибутом:

```markdown
![Загрузка по этапам](diagrams/workload.py){#fig:workload}
```

Такой файл выполняется тем же рендерером, в нём также доступны `plt` и `sns`;
сгенерированное изображение остаётся в кеше сборки.

### Диаграммы IDEF0

Блок `.idef0` строит рисунок по текстовому описанию. Для него требуется
та же установка с `.[plots]`, что и для графиков.

````markdown
```{.idef0 #fig:context caption="Контекстная диаграмма разработки"}
context A0 : Разработать систему
input : Заявка
output : Система
control : Договор

```
````

Внешний исходник подключается как `![Контекст](diagrams/context.idef0){#fig:context}`.
Для Python доступны пошаговый `idef0.Decomposition`, компактный `idef0.Waterfall`

Имена палитры и примеры с HEX приведены в разделе [«Цвет блоков, стрелок и подписей»](../idef0/README.md#цвет-блоков-стрелок-и-подписей).

### Рисунки: готовые изображения

Чтобы вставить собственное изображение (PNG, JPG или SVG) и получить подпись
«Рисунок N – ...» со сквозной нумерацией и возможностью ссылки из текста:

**Шаг 1.** Положите файл рядом с главами, обычно в подпапку `img/`:

```
my-thesis/
├── book.toml
├── CHAPTER_1.md
└── img/
    └── screenshot.png
```

**Шаг 2.** В нужном месте главы вставьте изображение. Путь — относительно
директории с главами (той, где `book.toml`); текст в `[...]` станет подписью,
а `{#fig:label}` — меткой для ссылки:

```markdown
![Главное окно системы](img/screenshot.png){#fig:screen}
```

**Шаг 3.** Сошлитесь на рисунок из текста через `[@fig:label]` — подставится
номер:

```markdown
Интерфейс системы представлен на рисунке [@fig:screen].
```

**Результат в документе:**

- изображение центрируется на странице;
- слишком большое изображение уменьшается до полосы набора: по ширине и по
  высоте (минус 1,2 см под подпись), пропорции сохраняются. Ширину pandoc
  подрезает сам, высоту — сборка: длинная PlantUML-диаграмма иначе уезжала бы
  за нижнее поле. Маленькая картинка остаётся в своём размере;
- под ним появляется подпись `Рисунок N – Главное окно системы`
  (стиль `GOSTImageCaption`, по центру), где `N` — сквозной номер;
- `[@fig:screen]` в тексте превращается в этот номер.

Подробности:

- Поддерживаются `.png`, `.jpg`, `.jpeg`, `.svg`.
- Нумерация **общая** с PlantUML-диаграммами: если выше была одна диаграмма
  (Рисунок 1), картинка станет Рисунком 2.
- Текст подписи берётся из `[...]` (alt). Можно переопределить атрибутом
  `caption="..."`, например
  `![](img/x.png){#fig:x caption="Схема БД"}`. Если подписи нет совсем —
  берётся заголовок ближайшего раздела. Нумерация и метка работают в обеих
  формах — и с alt-текстом, и без него.
- Метка `{#fig:label}` необязательна, но без неё нельзя сослаться `[@fig:...]`.
  Ссылка на несуществующую метку прерывает сборку.
- Не пишите «Рисунок N» и саму подпись вручную — их формирует сборка.

### Таблицы

Перед обычной Markdown-таблицей ставится HTML-комментарий-маркер с меткой и
подписью. Подпись `Таблица N – ...` выводится **над** таблицей, выровнена
**по левому краю без отступа** (стиль `GOSTTableCaption`):

```markdown
<!-- #tbl:tools Сравнение CASE-инструментов -->

| Инструмент | Лицензия  | Поддержка UML |
|------------|-----------|---------------|
| Tool A     | свободная | полная        |
| Tool B     | проприет. | частичная     |
```

- **Подпись обязательна для каждой таблицы.** Таблица без маркера прерывает
  сборку с ошибкой `table without a caption`: безымянную таблицу нельзя
  пронумеровать и на неё нельзя сослаться.
- `#tbl:tools` — метка для перекрёстной ссылки.
- Текст после метки — подпись таблицы.
- Шапка таблицы оформляется как заголовок (жирный, по центру);
  у обычной таблицы с `|` это первая строка;
  все ячейки получают одинарные чёрные границы, таблица центрируется и
  растягивается по ширине страницы.
- После каждой таблицы сборка вставляет одну пустую строку одинарного
  интервала, чтобы текст не прилипал к нижней границе. Вручную пустую строку
  после таблицы ставить не нужно.
- Маркер должен стоять **непосредственно** перед таблицей. Если между ними
  окажется абзац или что-то ещё, сборка прервётся с ошибкой — иначе подпись
  молча уехала бы к следующей таблице и сбила нумерацию.
- Альтернатива маркеру: заголовок `### Таблица ... – Подпись` тоже превращается
  в нумерованную подпись, но без перекрёстной ссылки. Работает только с уровня
  `###` и ниже, чтобы обычный раздел с названием «Таблица …» не был принят за
  подпись.

#### Сложные таблицы: объединения и многоуровневая шапка

Для объединения ячеек по строкам и столбцам используется формат Pandoc
`grid_tables`. Он дополняет обычные таблицы с `|`: существующие исходники,
маркеры, ссылки и настройки `book.toml` менять не нужно. Оба формата имеют
общую сквозную нумерацию.

```markdown
Результаты приведены в таблице [@tbl:plan].

<!-- #tbl:plan План и факт по этапам -->

+--------------+------------------+---------------------+
| Этап         | Показатель       | Значение            |
|              |                  +----------+----------+
|              |                  | План     | Факт     |
+==============+==================+==========+==========+
| Анализ       | Интервью         | 10       | 12       |
|              +------------------+----------+----------+
|              | Требования       | 20       | 18       |
+--------------+------------------+----------+----------+
```

- `+` отмечает углы и пересечения границ, `-` — горизонтальные границы,
  `|` — вертикальные. Границы выравниваются пробелами, без табуляции.
- Отсутствие вертикальной границы объединяет столбцы (`Значение`), отсутствие
  горизонтальной — строки (`Этап`, `Показатель`, `Анализ`). Пустой текст
  сам по себе ячейки не объединяет.
- Объединённая ячейка должна быть прямоугольной. Можно объединять одновременно
  по обеим осям, но нельзя пересекать границу между шапкой и данными.
- Шапка обязательна: один разделитель `+===+===+` на всю ширину отделяет
  все её строки от данных. Все строки шапки получают жирный шрифт,
  центрирование и признак повторения на следующей странице Word.
- Сверху и снизу таблица закрывается полной границей из `-` и `+`.
  Физические строки внутри таблицы не оставляют пустыми: пустую ячейку
  записывают пробелами между её границами.
- В первой версии поддерживаются текстовые ячейки, в том числе перенос
  текста внутри ячейки на несколько строк исходника. Абзацы, списки,
  вложенные таблицы, маркеры выравнивания `:` и настройка ширины столбцов
  не входят в этот формат. Длина линий в исходнике задаёт геометрию разметки;
  итоговую таблицу сборка растягивает по ширине страницы, как и обычную.
- `md-lint` проверяет геометрию как `STYLE005`, а `--fix` сохраняет сетку
  и выравнивающие пробелы. Требования к подписи и ссылкам остаются прежними.

### Листинги кода

Блок кода становится **листингом** — нумерованным вложением с подписью — как
только у него появляется подпись или метка. Подпись `Листинг N – ...` выводится
**над** кодом, по левому краю (стиль `GOSTListingCaption`):

````markdown
```{.python #lst:handler caption="Обработчик HTTP-запросов"}
def handle(request):
    return Response(200, json.loads(request.body))
```
````

Код можно не набирать в главе, а взять из файла — тело блока тогда остаётся
пустым:

````markdown
```{.python #lst:health file="src/handler.py" lines="11-12" caption="Проверка живости"}
```
````

- `#lst:handler` — метка для ссылки `[@lst:handler]`; подставляется голый
  номер: «приведён в листинге 2».
- `caption="..."` — текст подписи. Если его нет, берётся имя файла из `file=`,
  а если нет и его — заголовок ближайшего раздела.
- `file="path"` — путь относительно каталога работы (там, где `book.toml`), как
  у диаграмм и картинок. Файл с телом блока одновременно задать нельзя: сборка
  прервётся, а не станет выбирать за автора.
- `lines="11-12"` — какие строки файла вставить; без `file=` бессмысленно и
  тоже прерывает сборку. Нумерация строк — от единицы, границы включаются.
- **Нумерация листингов своя**, отдельная от рисунков, таблиц и формул.
- **Блок кода без подписи и метки листингом не считается**: он остаётся куском
  текста без номера. Так оформляют команды запуска и фрагменты конфигурации,
  на которые не ссылаются.
- `.python`, `.sql`, `.yaml` — класс языка. Подсветка синтаксиса выключена
  намеренно (`--syntax-highlighting=none`): на чёрно-белой печати цвета
  сливаются в неразличимый серый, а ГОСТ её и не предполагает.
- Код набирается Courier New 12 pt с одинарным интервалом и без абзацного
  отступа (стиль `Source Code`). Word длинные строки не переносит — строку
  длиннее ≈70 знаков стоит разбить в исходнике.
- После листинга сборка вставляет пустую строку, а подпись никогда не
  отрывается от кода разрывом страницы.

### Формулы

Формула набирается в LaTeX между `$$` **отдельным блоком** — с пустой строкой
до и после. Перед ней, как у таблицы, можно поставить маркер с меткой:

```markdown
<!-- #eq:maturity -->

$$K_{з} = \frac{\sum_{i=1}^{n} w_i x_i}{\sum_{i=1}^{n} w_i}$$

где $w_i$ — вес i-го критерия;
$x_i$ — оценка i-го критерия.
```

В документе формула встаёт по центру страницы, её номер `(N)` — у правого поля.
Технически это строка таблицы без границ в три колонки: пустая слева
уравновешивает колонку с номером, иначе формула съехала бы влево на её ширину.
Абзац Word выравнивается либо по центру, либо по правому краю, но не так и так
сразу, отсюда и таблица.

- **Номер получает каждая выключная формула**, метка на нумерацию не влияет —
  она нужна только затем, чтобы на формулу сослаться. Нумерация сквозная по
  всему документу, своя, отдельная от рисунков и таблиц.
- `<!-- #eq:label -->` — метка. В отличие от таблицы, текста в маркере нет:
  у формулы есть номер, но не подпись. Текст в маркере прерывает сборку.
- Маркер должен стоять **непосредственно** перед формулой — иначе сборка
  прервётся, как и с оторванным маркером таблицы.
- Ссылка `[@eq:maturity]` подставляет номер **в скобках**: «по формуле (1)».
  Так номер формулы и пишется по ГОСТ, в отличие от рисунка и таблицы, где
  подставляется голое число.
- Выше и ниже формулы сборка оставляет свободную строку.
- **Экспликация** — абзац сразу за формулой, начинающийся со слова «где», —
  становится продолжением той же таблицы: «где» уходит в первую колонку, а
  расшифровки занимают остальные, поэтому все обозначения начинаются на одной
  вертикали и выравниваются по ширине, как основной текст. Пишется она **одним абзацем**: строки внутри разделяются простым
  переводом строки, без пустой строки между ними, иначе в таблицу попадёт
  только первая (ошибка линтера `EQ004`). Абзац «где …», стоящий не сразу за
  формулой, остаётся обычным текстом.
- Формула не разрывается страницей: строка таблицы помечена `cantSplit`.
- **Формула внутри абзаца** (`текст $$a=b$$ текст`) остаётся в строке и номера
  не получает — линтер сообщает об этом ошибкой `EQ002`.
- Формулы **в строке текста** набираются одиночными `$`: `$w_i$` — это обычная
  математика внутри абзаца, она никуда не переносится и не нумеруется.
- Математика попадает в документ как родная формула Word (OMML), а не как
  картинка: её можно править в редакторе формул. Шрифт и кегль наследуются от
  стиля `GOSTFormula` — TNR 14.

### Перекрёстные ссылки

В тексте ссылайтесь на метки через `[@...]` — подставится голый номер:

```markdown
Как показано на рисунке [@fig:usecase], ...
Данные приведены в таблице [@tbl:tools].
Точка входа приведена в листинге [@lst:handler].
Показатель рассчитывается по формуле [@eq:maturity].
```

`[@fig:usecase]` → `1`, `[@tbl:tools]` → `1`, `[@lst:handler]` → `1`,
`[@eq:maturity]` → `(1)`: номер формулы подставляется в скобках, остальные —
голым числом. Ссылка на
несуществующую метку прерывает сборку с ошибкой (это защита от «битых» ссылок).

### Список литературы

Источники объявляются маркерами `#bib:key` (где угодно, удобно — в отдельном
`REFERENCES.md`):

```markdown
<!-- #bib:urintsov Уринцов, А. И. Управление знаниями... — Москва, 2021. — 255 с. -->
<!-- #bib:bpmn Богословская, Н. В. Моделирование бизнес-процессов... — СПб, 2022. -->
```

Цитирование в тексте — `[@bib:key]`, можно несколько через `;`:

```markdown
... как отмечают авторы [@bib:urintsov], ...
... в работах [@bib:urintsov; @bib:bpmn] ...
```

- В тексте подставляются номера в квадратных скобках: `[1]`, `[1, 2]`.
- Номера присваиваются **в порядке первого цитирования**.
- В конце документа автоматически добавляется раздел
  «Перечень использованных информационных ресурсов» с пронумерованным списком
  (стиль `GOSTBibliography`). Попадают только реально процитированные источники.
- Дубликат определения `#bib:key` или ссылка на необъявленный ключ прерывают
  сборку с ошибкой.

### Тире

Длинное тире `—` (em-dash) автоматически заменяется на короткое `–` (en-dash)
по всему документу: в основном тексте, в ячейках таблиц (включая вложенные), в
сносках, надписях и колонтитулах. Замена идёт по всем текстовым узлам пакета,
так что обойти её нельзя — писать `—` в исходнике можно свободно.

## Что получается на выходе: стили ГОСТ

Каждый смысловой элемент имеет **собственный** именованный стиль Word, поэтому
его легко переопределить вручную в панели стилей.

| Стиль Word | Назначение | Оформление |
|------------|------------|------------|
| `Normal` | основной текст | TNR 14, по ширине, интервал 1,5, отступ 1,25 см |
| `Heading 1` | заголовок главы | TNR 16, жирный, с новой страницы (`page_break_before_h1`) |
| `Heading 2` | подзаголовок | TNR 14, жирный |
| `Heading 3` | под-подзаголовок | TNR 14, жирный |
| `GOSTImageCaption` | подпись рисунка | TNR 12, **по центру**, без отступа |
| `GOSTTableCaption` | подпись таблицы | TNR 12, **по левому краю**, без отступа |
| `GOSTFormula` | выключная формула | TNR 14, по центру, без отступа |
| `GOSTFormulaNumber` | номер формулы | TNR 14, по правому краю, без отступа |
| `GOSTExplanation` | экспликация «где …» | TNR 14, по ширине, без отступа |
| `GOSTListingCaption` | подпись листинга | TNR 12, по левому краю, без отступа |
| `Source Code` | код листинга | Courier New 12, интервал 1, без отступа, чёрный |
| `GOSTBibliography` | элемент списка литературы | TNR 14, по ширине, интервал 1,5 |

Общие параметры страницы: формат **A4** (210×297 мм), поля 30/10/20/20 мм
(лево/право/верх/низ), базовый шрифт темы заменён на Times New Roman. Если
включена [рамка](#рамка-гост-основная-надпись), поля переопределяются под неё.

## Рамка ГОСТ (основная надпись)

Опционально документ обрамляется рамкой со штампом по ГОСТ. Рамка нарисована
векторно (VML) в двух колонтитулах:

- **первая страница** — большой штамп (форма 2, 40 мм);
- **последующие страницы** — малый штамп (форма 2а) с авто-нумерацией листов
  (поле `PAGE`).

Включается таблицей `[frame]` в `book.toml` (или `frame = true` для значений по
умолчанию). Параметры штампа:

| Ключ | Поле штампа | По умолчанию |
|------|-------------|--------------|
| `author` | Разраб. | `Иванов И.И.` |
| `checker` | Провер. | `Петров П.П.` |
| `title` | наименование документа | `Отчет по ... практике` |
| `org` | организация | `ДГТУ, кафедра «ИТ»` |
| `designation` | обозначение | `УП.280000.000` |
| `sheets` | Листов (всего) | `55` |
| `first_sheet` | № листа на 1-й странице | `1` |
| `page_start` | начало нумерации страниц | `1` |

Геометрия рамки рассчитана под A4 и специальные поля, поэтому при включённой
рамке размер листа и поля задаются автоматически (их не нужно настраивать).

> **Шрифт штампа.** Текст основной надписи использует чертёжный шрифт
> **ISOCPEUR**. Если он не установлен в системе, Word подставит другой шрифт —
> сама рамка и её геометрия от этого не страдают.

> **Замечание.** Рамка применяется ко всему документу, включая первую страницу.
> Если перед основным текстом нужны титульный лист и задание без рамки, их
> готовят отдельным файлом и сшивают с результатом вручную.

## Как устроена сборка

Команда `md-gost build` вызывает функцию `build()` из `gost_builder/pipeline.py`.
При запуске из исходников `python md_to_gost.py` вызывает ту же точку входа.

0. **Манифест.** Сборщик читает порядок глав и параметры документа из `book.toml`,
   проверяет наличие программ и заголовки для автоматической нумерации.
1. **Pre-lint Markdown.** Линтер проверяет главы. Ошибки прерывают
   сборку, предупреждения печатаются. Проверка отключается флагом `--no-lint`.
2. **Шаблон.** Генерирует свежий `reference.docx` со стилями ГОСТ и форматом A4
   (`gost_builder/reference/`) в кеше `<dir>/.md-to-gost/`.
3. **Pandoc.** Собирает главы с Lua-фильтром `gost_builder/filters/plantuml.lua`
   (диаграммы, подписи, нумерация, листинги, библиография) и выключенной
   подсветкой синтаксиса. PlantUML-диаграммы — и
   inline-блоки, и обёртки над вставленными файлами — пишутся
   в `<dir>/.md-to-gost/img/`; путь передаётся фильтру через переменную
   окружения `MD2GOST_IMG_DIR`. Команда PlantUML передаётся туда же
   (`MD2GOST_PLANTUML`, при jar ещё и `MD2GOST_PLANTUML_PREFIX` с `-jar` и путём).
   Все диаграммы рендерятся **одним** вызовом в конце обхода: запуск JVM на
   каждую диаграмму стоил бы больше, чем вся остальная сборка.
4. **Постобработка.** Пакет `gost_builder/postprocess/` приводит к ГОСТу списки, рисует
   границы таблиц, снимает их с таблиц-формул, центрирует изображения и — если
   работа не отключила это ключом `page_break_before_h1` — ставит разрывы
   страниц перед `Heading 1`. Класс `.page` ставит такой же разрыв у одного
   заголовка. Подписи и список литературы сюда не попадают: фильтр помечает
   их атрибутом `custom-style`, и стиль Word проставляет сам pandoc.
5. **Рамка** (если задана `[frame]`). Пакет `gost_builder/frame/` встраивает в DOCX два
   колонтитула с рамкой и штампом, подставляет параметры штампа, переопределяет
   размер листа и поля под рамку.
6. **Post-lint OOXML.** встроенный постлинтер читает `word/document.xml`
   из готового пакета, проверяет разрывы строк таблиц и подозрительно крупные
   изображения. Это предупреждения о риске верстки, а не точная оценка
   свободного места: OOXML не хранит координаты элементов на страницах.
7. **Проверка целостности.** Контролирует zip-архив docx и считает вложенные
   медиа-файлы.

Промежуточные артефакты складываются в `<dir>/.md-to-gost/` и не мешают
исходникам. Выходной `.docx` кладётся рядом с `book.toml`.

## Устранение проблем

- **`md-lint found errors`** — pre-lint нашёл нарушения правил оформления текста;
  они перечислены выше сообщения. Исправьте их или соберите с `--no-lint`.
- **`pandoc not found`** — установите Pandoc: Homebrew, `winget install --source winget --exact --id JohnMacFarlane.Pandoc`
  или `pypandoc.download_pandoc()`. См. [требования](#требования).
- **`plantuml not found on PATH`** — в главах есть ```` ```plantuml ````-блоки
  или вставленные файлы `.puml`/`.iuml`, а команда `plantuml` и файл
  `plantuml.jar` не найдены. Положите jar в каталог из `PATH` или задайте
  `PLANTUML_JAR`. Сборка прерывается: молча выпустить документ, где вместо
  диаграммы кусок разметки, хуже, чем упасть.
- **`java not found on PATH`** — jar найден, а `java` нет. Поставьте JDK
  (на Windows: `winget install --source winget --exact --id EclipseAdoptium.Temurin.21.JDK`).
- **`which Pandoc cannot execute`** — в `PATH` есть `plantuml.bat` или
  `plantuml.cmd`, а `plantuml.jar` рядом нет. Pandoc такой файл не запускает.
- **`dot (Graphviz) was not found`** — предупреждение, не ошибка. Часть
  диаграмм PlantUML рисует без `dot`. Установка: `winget install graphviz`,
  `choco install graphviz`, `brew install graphviz`, <https://graphviz.org/download/>.
- **`plantuml rendered no png/svg for: diagram_NN`** — PlantUML запустился, но эту
  диаграмму не отрисовал. Ищите синтаксическую ошибку в её теле; исходник
  остаётся в `<dir>/.md-to-gost/img/diagram_NN.puml` (для вставленного файла
  там лежит обёртка с `!include` — она показывает, какой файл искали).
- **`diagram file not found: ...`** — путь к `.puml`/`.iuml` в главе не ведёт
  к файлу. Он отсчитывается от директории с `book.toml`, а не от самой главы.
- **`Undefined cross-reference: [@fig:...]`** — ссылка на метку, которой нет.
  Проверьте, что метка объявлена (`#fig:label`, `#tbl:label`, `#eq:label`,
  `#bib:key`).
- **`Duplicate ... label/definition`** — метка или источник объявлены дважды.
- **`... is not immediately followed by a table`** — между маркером
  `<!-- #tbl:... -->` и таблицей что-то вклинилось.
- **`... is not immediately followed by a $$...$$ formula`** — то же самое с
  маркером `<!-- #eq:... -->`: между ним и формулой оказался другой блок либо
  формула набрана внутри абзаца.
- **`a formula has a number, not a caption`** — в маркере `<!-- #eq:... -->`
  написан текст. У формулы подписи нет, в маркере остаётся только метка.
- **`listing file not found: ...`** — путь в `file="..."` не ведёт к файлу; он
  отсчитывается от каталога с `book.toml`, а не от самой главы.
- **`the fence has both file="..." and a body`** — у листинга задан и файл, и
  собственный текст. Оставьте что-то одно.
- **Блок кода не получил номера** — у него нет ни `caption=`, ни `#lst:`-метки,
  а без них он листингом не считается.
- **Расшифровка обозначений не выровнялась под формулой** — экспликация
  разбита на абзацы пустыми строками. Соберите её в один абзац, разделяя
  строки переводом строки (это же ловит линтер правилом `EQ004`).
- **`WARNING — declared but never cited`** — источник объявлен через `#bib:`, но
  ни разу не процитирован, и в список не попал. Обычно это опечатка в ключе.
- **`number_sections is on, but these headings already carry a number`** — в
  главе остался номер, набранный руками. Уберите его из заголовка (сборка
  проставит свой) или выключите `number_sections`; раздел, который номера
  иметь не должен, помечается `{-}`.
- **`no book.toml`** — в директории нет манифеста; создайте его (см. выше).
- **Штамп в рамке набран не тем шрифтом** — не установлен ISOCPEUR; Word
  подставил замену. Поставьте шрифт ISOCPEUR или примите подстановку.
- **Текст налезает на рамку** — проверьте поля страницы. При включённой
  рамке их задаёт пакет `gost_builder/frame/`.
- **Ошибки сети при первом запуске** — venv ставит зависимости через pip;
  нужен доступ к индексу пакетов. После успешной установки сеть не требуется.
- **Переустановить инструмент** — выполните `uv tool install --force .` из
  корня репозитория; кеш работы можно удалить в `<dir>/.md-to-gost/`.

## Проверки кода

```bash
cd packages/md-gost-build
uvx ruff check .      # стиль и типичные ошибки (то же гоняет pre-commit)
uvx ruff format .     # раскладка кода (тоже в pre-commit)
uvx pyrefly check     # типы, режим strict
```

Настройки обоих — в `pyproject.toml` этого инструмента: он самостоятельный
продукт, общей конфигурации на репозиторий нет.

## Тесты

Тесты лежат в `tests/` и запускают сборщик с Python из тестового окружения.
Установите зависимости для тестов и графиков через `uv run`:

```bash
cd packages/md-gost-build
uv run --group dev --extra plots pytest                  # весь набор
uv run --group dev --extra plots pytest -m "not build"   # без реальных сборок
uv run --group dev --extra plots pytest --update-golden   # обновить слепок
```

Для полного набора нужны Pandoc и PlantUML (команда или `plantuml.jar`).

| Файл | Что проверяет |
|------|---------------|
| `tests/test_golden.py` | сборка `example/` совпадает с `tests/golden.json` |
| `tests/test_negative.py` | ошибочная разметка прерывает сборку |
| `tests/test_features.py` | заголовки, тире, масштабирование рисунков |
| `tests/conftest.py` | обёртки сборки и фикстуры временных работ |

Золотой тест собирает `example/` и сверяет текстовый слой, последовательность
стилей абзацев, число вложенных изображений и поля штампа с
`tests/golden.json`. Негативные тесты проверяют, что битая перекрёстная ссылка,
дублирующаяся метка, неизвестный источник, его дубликат и оторванный маркер
таблицы **прерывают** сборку, а не проходят молча. Сборки в тестах идут с
`--no-lint`: это тесты сборщика, у линтера свой набор — кроме одного случая,
который как раз проверяет, что ошибка линтера сборку останавливает.

После любой правки `gost_builder/` собирайте `example/`: золотой тест сверяет
именно его.
